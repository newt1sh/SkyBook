### 3.2. Виконання Fetch-запитів

Для дослідження HTTP-запитів у JavaScript було використано сервіс JSONPlaceholder.

**Запит 1 – отримання одного запису:**

```javascript
const response = await fetch(
  "https://jsonplaceholder.typicode.com/posts/1"
);
console.log(await response.json());
```

У відповіді отримано JSON-об'єкт із полями `userId`, `id`, `title` та `body`.

**Запит 2 – отримання списку записів:**

```javascript
const posts = await (
  await fetch("https://jsonplaceholder.typicode.com/posts")
).json();

console.table(posts.slice(0, 5));
```

Отримано список публікацій. Для зручності перші п'ять записів виведено у вигляді таблиці.

**Запит 3 – отримання коментарів до публікації:**

```javascript
const comments = await (
  await fetch(
    "https://jsonplaceholder.typicode.com/posts/1/comments"
  )
).json();

console.table(comments);
```

Отримано список коментарів, пов'язаних із першою публікацією.

**Запит 4 – фільтрація коментарів:**

```javascript
const filtered = await (
  await fetch(
    "https://jsonplaceholder.typicode.com/comments?postId=1"
  )
).json();

console.table(filtered);
```

У запиті використано параметр `postId=1`, який дозволяє отримати коментарі до конкретної публікації.

**Результат:** усі чотири Fetch-запити виконано успішно. Отримані відповіді було оброблено у форматі JSON.

Знімки екрана:
- `fetch-posts.png` – перший і другий запити;
- `fetch-comments.png` – третій і четвертий запити.

### 3.3. Дослідження HTTP-запитів за допомогою curl

Для виконання запитів у терміналі Git Bash було використано утиліту `curl.exe`.

Було виконано дев'ять запитів:

| № | Метод | Запит | Результат |
|---|---|---|---|
| 1 | GET | `/posts/1` | 200 OK – отримано один запис |
| 2 | GET | `/posts?userId=1&_limit=3` | 200 OK – отримано три записи |
| 3 | POST | `/posts` | 201 Created – створено тестовий запис |
| 4 | PUT | `/posts/1` | 200 OK – повністю оновлено запис |
| 5 | PATCH | `/posts/1` | 200 OK – частково оновлено запис |
| 6 | DELETE | `/posts/1` | 200 OK – виконано тестове видалення |
| 7 | GET | `/posts/99999` | 404 Not Found – ресурс не знайдено |
| 8 | HEAD | `/posts` | 200 OK – отримано заголовки без тіла відповіді |
| 9 | GET | GitHub API `/users/octocat` | 200 OK – отримано інформацію про користувача |

Під час POST-запиту було передано JSON із полями `title`, `body` та `userId`. У відповіді сервер повернув код 201 Created та ідентифікатор створеного запису.

Під час PUT-запиту було виконано повну заміну даних запису, а під час PATCH – змінено лише поле `title`.

Для DELETE-запиту сервер повернув успішну відповідь. JSONPlaceholder є тестовим сервісом, тому операції зміни даних моделюються та не зберігаються постійно.

Під час виконання HEAD-запиту було отримано заголовки відповіді без її основного вмісту.

### 3.4. Дослідження кодів стану HTTP 404, 401 та 304

Було змодельовано три ситуації.

**1. Код 404 Not Found**

Запит:

```bash
curl.exe -i https://jsonplaceholder.typicode.com/posts/99999
```

Отримано відповідь `404 Not Found`. Це означає, що запитуваний ресурс не існує або не знайдений сервером.

**2. Код 401 Unauthorized**

Запит:

```bash
curl.exe -i https://api.github.com/user
```

Отримано відповідь `401 Unauthorized` із повідомленням про необхідність авторизації. Це означає, що для доступу до ресурсу потрібні відповідні облікові дані.

**3. Код 304 Not Modified**

Спочатку було отримано ETag користувача GitHub через запит:

```bash
curl.exe -i https://api.github.com/users/octocat
```

Після цього було виконано умовний запит із заголовком `If-None-Match`:

```bash
curl.exe -i -H "If-None-Match: W/\"d9edcef5f37b5b4c1756eeff21fc49cc15de3a424aee8e881ca266046bf7a2b8\"" https://api.github.com/users/octocat
```

Сервер повернув `304 Not Modified`. Це означає, що ресурс не змінився порівняно з попередньою версією, тому клієнт може використати збережену копію з кешу.

### 3.5. Дослідження Dog CEO API

Для виконання індивідуального завдання було обрано публічний API Dog CEO.

Адреса документації: https://dog.ceo/dog-api/

Було виконано п'ять успішних запитів.

**Запит 1 – отримання списку всіх порід собак:**

```bash

```

Отримано JSON-об'єкт із полем `message`, що містить перелік порід та їх підпорід, і полем `status`, яке має значення `success`.

**Запит 2 – отримання випадкового зображення собаки:**

```bash

```

У відповіді поле `message` містить URL випадкового зображення собаки, а `status` – результат виконання запиту.

**Запит 3 – отримання всіх зображень лабрадорів:**

```bash
curl.exe -i https://dog.ceo/api/breed/labrador/images
```

Отримано масив URL-адрес зображень породи Labrador.

**Запит 4 – отримання випадкового зображення бігля:**

```bash
curl.exe -i https://dog.ceo/api/breed/beagle/images/random
```

У відповіді отримано посилання на випадкове зображення собаки породи Beagle.

**Запит 5 – отримання трьох випадкових зображень бігля:**

```bash
curl.exe -i "https://dog.ceo/api/breed/beagle/images/random/3?source=lab02"
```

Отримано масив із трьох URL-адрес зображень породи Beagle.

У цьому запиті також було використано query-параметр `source=lab02`. Запит успішно оброблено, однак цей параметр не вплинув на результат, оскільки API використовує переважно параметри, задані в URL-шляху.

**Структура відповіді API:**

Основними елементами відповідей є:

- `message` – дані відповіді: URL, масив URL або об'єкт із переліком порід;
- `status` – результат виконання запиту, наприклад `success`.

Під час додаткової перевірки некоректних URL було отримано відповіді 404, коли вказувалися назви порід або підпорід, які API не розпізнає.

**Висновок за завданням:** Dog CEO API дозволяє отримувати інформацію про породи собак та зображення за допомогою HTTP-запитів. Відповіді повертаються у форматі JSON.

### 3.6. Проєктування REST API для SkyBook

На основі предметної області проєкту SkyBook було розроблено перелік ресурсів для роботи з аеропортами, авіарейсами, квитками та пасажирами.

Результат оформлено у файлі `docs/api-design.md`.

Основні кінцеві точки API:

| № | Метод | URL | Призначення |
|---|---|---|---|
| 1 | GET | `/airports` | Отримання списку аеропортів |
| 2 | GET | `/airports/:id` | Отримання інформації про аеропорт |
| 3 | GET | `/flights` | Пошук авіарейсів |
| 4 | GET | `/flights/:id` | Отримання інформації про рейс |
| 5 | GET | `/flights/:id/tickets` | Перегляд квитків на рейс |
| 6 | POST | `/tickets` | Створення бронювання |
| 7 | GET | `/tickets/:id` | Отримання інформації про квиток |
| 8 | PATCH | `/tickets/:id` | Часткове оновлення квитка |
| 9 | DELETE | `/tickets/:id` | Скасування бронювання |
| 10 | GET | `/passengers/:id/tickets` | Отримання квитків пасажира |

Для пошуку рейсів передбачено query-параметри `from`, `to`, `date`, `maxPrice`, `sort` та `page`.

Приклад запиту:

```http
GET /flights?from=KBP&to=JFK&date=2026-12-01&maxPrice=500
```

Також було розроблено приклад POST-запиту для створення бронювання квитка з передаванням ідентифікаторів рейсу та пасажира, а також номера місця.

Для помилок валідації передбачено JSON-відповідь із кодом `VALIDATION_FAILED`.

### 3.7. Діаграма послідовності

Для проєкту SkyBook було створено діаграму послідовності процесу пошуку авіарейсів.

У діаграмі відображено взаємодію чотирьох учасників:

- користувач;
- браузер;
- сервер;
- база даних.

Користувач вводить напрямок і дату польоту. Браузер надсилає GET-запит до сервера. Сервер звертається до бази даних, отримує список рейсів та повертає браузеру відповідь зі статусом 200 OK і JSON-даними. Після цього браузер відображає результати користувачу.

Діаграму збережено у файлі `labs/lab02/sequence-diagram.md`.

## 4. Відповіді на контрольні запитання

**1. Поясніть принцип роботи клієнт-серверної архітектури у веб-середовищі.**

Клієнт-серверна архітектура передбачає взаємодію двох основних компонентів: клієнта та сервера. Клієнт (браузер) відповідає за відображення інформації та взаємодію з користувачем. Сервер обробляє запити, виконує бізнес-логіку та взаємодіє з базою даних. Обмін інформацією здійснюється за допомогою протоколу HTTP або HTTPS.

**2. Із яких частин складається HTTP-запит і HTTP-відповідь?**

HTTP-запит складається зі стартового рядка, заголовків, порожнього рядка та необов'язкового тіла запиту. Стартовий рядок містить метод, адресу ресурсу та версію HTTP.

HTTP-відповідь складається з рядка стану, заголовків, порожнього рядка та необов'язкового тіла відповіді. Рядок стану містить версію HTTP, код стану та текстовий опис.

**3. Чим відрізняються методи GET, POST, PUT, PATCH і DELETE?**

- GET – отримання ресурсу.
- POST – створення нового ресурсу.
- PUT – повна заміна ресурсу.
- PATCH – часткове оновлення ресурсу.
- DELETE – видалення ресурсу.

**4. Що означає ідемпотентність методу? Наведіть приклади ідемпотентних і неідемпотентних методів.**

Ідемпотентність означає, що повторне виконання однакового запиту приводить до такого самого кінцевого стану ресурсу, як і одноразове виконання.

Ідемпотентними є GET, PUT і DELETE. Неідемпотентним є POST. PATCH не гарантує ідемпотентності.

**5. Назвіть групи кодів стану HTTP та наведіть по два приклади з кожної.**

- 1xx – інформаційні: 100 Continue, 101 Switching Protocols.
- 2xx – успішне виконання: 200 OK, 201 Created.
- 3xx – перенаправлення або використання кешу: 301 Moved Permanently, 304 Not Modified.
- 4xx – помилки клієнта: 400 Bad Request, 404 Not Found.
- 5xx – помилки сервера: 500 Internal Server Error, 503 Service Unavailable.

**6. Які коди слід повертати у разі успішного створення, успішного видалення та помилки валідації?**

- 201 Created – успішне створення ресурсу.
- 204 No Content – успішне видалення без повернення тіла відповіді.
- 422 Unprocessable Content – помилка валідації переданих даних.

**7. Що таке REST і які правила іменування ресурсів він передбачає?**

REST – архітектурний стиль побудови вебсервісів, у якому дані представляються як ресурси з унікальними адресами. Для роботи з ресурсами використовуються HTTP-методи. В адресах зазвичай використовуються іменники у множині, а не дієслова.

**8. Чому HTTP називають протоколом без збереження стану і як розв'язується задача автентифікації?**

HTTP називають протоколом без збереження стану, оскільки кожен запит обробляється незалежно від попередніх. Для автентифікації використовуються cookie, серверні сесії або токени, наприклад JWT, які передаються у заголовках запитів.

**9. Які можливості надає вкладка Network інструментів розробника?**

Вкладка Network дозволяє переглядати HTTP-запити та відповіді, їхні URL, методи, коди стану, заголовки, тіла відповідей, типи ресурсів і час завантаження.

**10. Що таке CORS і за яких умов браузер надсилає попередній запит OPTIONS?**

CORS – механізм безпеки браузера, який регулює доступ вебсторінок до ресурсів іншого джерела. Попередній запит OPTIONS надсилається перед основним запитом, якщо він не відповідає умовам простого CORS-запиту, наприклад використовує нестандартні заголовки або метод PUT чи DELETE.

**11. Для чого призначені заголовки Cache-Control, ETag і If-None-Match?**

- Cache-Control визначає правила кешування ресурсів.
- ETag є ідентифікатором певної версії ресурсу.
- If-None-Match використовується для умовних запитів і перевірки, чи змінився ресурс.

Якщо ресурс не змінився, сервер може повернути 304 Not Modified, після чого клієнт використовує збережену копію.
